# CashRadar: архитектура

Статус: этап 2, 11.11.2026. Источник требований — [мастер-ТЗ](cash_radar_brd.md). Облачный проект и локальный Supabase настроены, подключение и базовая авторизация проверены. Подробности — в [инструкции по настройке](setup.md).

## Назначение и границы

CashRadar — персональный финансовый трекер с потенциальной поддержкой нескольких пользователей. Целевые клиенты — Flutter Web, Android и iOS. На старте основой служат ручной учёт и импорт выписок; автоматический сбор и аналитика добавляются по этапам. Не создавать будущие модули и таблицы заранее.

## Предлагаемая структура

```text
Cash-Radar/
  docs/                      # мастер-ТЗ, архитектура, решения, план
  app/                       # Flutter-приложение (создаётся на этапе 1)
    lib/
      app/                   # настройка приложения, маршруты и тема
      core/                  # только реально общие компоненты
      features/<feature>/    # по необходимости: data, domain, presentation
    test/
    android/ ios/ web/
  supabase/                  # настройки, миграции и функции Supabase
    migrations/
    functions/               # серверная логика по мере необходимости
```

Это целевая схема, а не перечень каталогов, которые необходимо создать сразу. Git-репозиторий расположен в едином корне, без разделения на микросервисы. Фактическая структура и версии зависимостей выбираются при реализации и проверяются на совместимость с установленным SDK.

## Компоненты и потоки данных

1. Flutter содержит интерфейс и клиентские сценарии. Riverpod и GoRouter вводятся по мере необходимости; Drift — когда появится обоснованная потребность в офлайн-кэше и будет определена стратегия синхронизации.
2. Размещённый Supabase предоставляет PostgreSQL, Auth, Storage и Edge Functions. Это единый backend с логическими модулями, а не набор микросервисов. Сложная и финансово значимая логика выполняется на сервере; RLS и ограничения БД действуют независимо от интерфейса.
3. Выписка в будущем загружается в закрытое хранилище, проходит проверку и детерминированный парсер конкретного банка, затем предварительный просмотр и подтверждение. Файл, пакет импорта, исходные данные и канонические операции связываются; повторная обработка должна быть идемпотентной.
4. Android-уведомления после явного разрешения создают предварительные операции; банковские выписки подтверждают их через осторожное сопоставление. iOS не читает уведомления других приложений. Доступ к выделенному Gmail будет добавлен после готовности импорта и парсеров.
5. Правила категоризации применяются до опционального Gemini на сервере. Модели передаются только минимальные обезличенные данные; JSON-ответ проверяется, пороги уверенности настраиваются. Полные выписки и ключ API в клиент не передаются. Модель и тариф необходимо проверить непосредственно на этапе интеграции.

Для пользовательских CRUD-операций допустим прямой доступ клиента к Supabase с публичным ключом при корректной авторизации, RLS и ограничениях БД. Операции, которым нужны секреты, привилегии или атомарная бизнес-логика, выполняются через серверные функции / контролируемые процедуры. При появлении длительного парсинга или Gmail-обработки сначала измерить лимиты Edge Functions: тяжёлый процесс может потребовать отдельного фонового исполнителя, не меняя границ домена.

## Данные и финансовые правила

- В каждой пользовательской сущности и в доступе к файлам учитывается владелец. Связи между счетами, категориями, импортами и операциями должны проверять совпадение владельца на уровне БД и серверных операций. Глобальные справочники и пользовательские записи получают отдельные политики.
- Суммы хранятся точно: PostgreSQL `numeric` либо целые минимальные единицы с явно заданным масштабом валюты; двоичный `float` для денежных расчётов не используется. Конкретный формат и округление утвердить при проектировании схемы. Сумма покупки и сумма списания, обе валюты и исходное описание сохраняются независимо.
- Курсы являются отдельными данными с датой и источником; при отсутствии курса не подставлять вымышленные значения. Pending не включается в окончательную статистику. Подтверждённые внутренние переводы не считаются доходом или расходом; неоднозначные связи предлагаются пользователю.
- Сопоставление источников учитывает банк, счёт, идентификатор, сумму, валюту, дату и описание; приоритет и аудит решения должны быть явными. Для неоднозначных совпадений не выполнять автоматическое объединение. Детальные правила и ограничения проектируются на соответствующих этапах.

## Безопасность и эксплуатация

- Auth устанавливает личность; сервер проверяет токен, RLS изолирует строки. Приватные бакеты и политики Storage отдельно ограничивают доступ к оригиналам выписок; имена и метаданные файлов тоже могут быть чувствительны.
- Публичные URL и publishable/anon key предназначены для клиента и не являются секретом; привилегированные service/secret keys, доступы к БД и ключ Gemini хранятся только на сервере. Секреты и реальные выписки исключаются из Git-репозитория.
- Использовать минимальные права, TLS, безопасное хранение сессий и обезличенные логи; не сохранять банковские пароли и не обходить системные ограничения.
- Миграции версионируются; применённые удалённые миграции не переписываются. Тесты изоляции проверяют двух пользователей, прямые запросы, связанные объекты и Storage. Перед использованием реальных данных нужно отдельно проверить восстановление из резервной копии и ограничения Free-плана; наличие автоматического восстановления не предполагается.
- Для бесплатного проекта возможна пауза при низкой активности. Нужно показывать понятную ошибку и предусмотреть восстановление; не рассчитывать на непрерывную работу фоновых задач.

## Инфраструктура и инструменты

Выбранный предварительный вариант — управляемый **Supabase Free** для PostgreSQL/Auth/Storage и Edge Functions, один выделенный облачный проект на старте; локальная среда — Supabase CLI и Docker-совместимая среда, когда она доступна. Проект Cash Radar создан владельцем в регионе `ap-northeast-1` (Токио); регион подтверждён владельцем. Раздельные dev/prod-проекты зависят от свободной квоты; локальная разработка не заменяет отдельное production-окружение, а реальные данные нельзя использовать как тестовые.

На 11.11.2026 официальные страницы указывают: до двух активных бесплатных проектов в пределах лимита аккаунта, 500 MB БД на проект, 1 GB файлового хранилища, 5 GB egress и 50 000 MAU; область действия конкретных квот и актуальные лимиты проверить в панели перед созданием. При низкой активности в течение недели проект могут приостановить. Free Edge Functions ограничены, в частности, 256 MB памяти, 2 сек. CPU на запрос и 150 сек. временем жизни worker: пригодность тяжёлого парсинга нужно проверять отдельно. Условия могут измениться.

Источники: [тарифы Supabase](https://supabase.com/pricing), [правила биллинга и квот](https://supabase.com/docs/guides/platform/billing-on-supabase), [приостановка Free-проектов](https://supabase.com/docs/guides/platform/free-project-pausing), [лимиты Edge Functions](https://supabase.com/docs/guides/functions/limits), [локальная разработка](https://supabase.com/docs/guides/local-development).

Для статического Flutter Web по обновлённому ТЗ выбраны Cloudflare Pages с публикацией из Git на этапе 4; Cloudflare Functions и Workers не используются как backend. По состоянию на 11.11.2026 Free-план указывает 500 сборок в месяц, одну одновременную сборку и до 20 000 файлов на сайт; запросы к статическим ресурсам бесплатны. Условия и размер сборки нужно повторно проверить перед публикацией: [лимиты Cloudflare Pages](https://developers.cloudflare.com/pages/platform/limits/), [статические запросы](https://developers.cloudflare.com/pages/functions/pricing/). Не включать платные услуги без согласия владельца.
