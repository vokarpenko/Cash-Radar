# CashRadar: архитектурные решения

Записано 11.11.2026 по результатам этапа 0. Решения предварительные и уточняются при реализации соответствующего этапа.

## ADR-001. Единое рабочее пространство

**Решение:** разместить документацию, Flutter-приложение и конфигурацию Supabase в текущем каталоге; приложение — в `app/`, серверные артефакты — в `supabase/`. Подробная структура приведена в [архитектуре](architecture.md).

**Причина:** проект новый, существующих соглашений нет; один корень упрощает будущий Git и отслеживание миграций вместе с клиентом. После этапа 0 пользователь создал Git-репозиторий `Cash-Radar`.

## ADR-002. Управляемый Supabase для MVP

**Решение:** выбрать Supabase Free: PostgreSQL, Auth, Storage и Edge Functions как основу модульного монолита. На этапе 1 планируется один облачный проект с локальной средой для разработки; возможность второго облачного окружения зависит от свободной квоты. Владелец создал проект в Токио; подробности — в ADR-007.

**Причина:** согласуется с ТЗ, объединяет ключевые сервисы и сокращает начальные затраты. Компромиссы — зависимость от платформы, лимиты ресурсов, возможная приостановка и необходимость отдельно решить резервное копирование и фоновые задачи. Переносимость поддерживается обычным PostgreSQL, миграциями и локализацией Supabase-специфичных интеграций, но автоматический бесшовный перенос не обещается.

На 11.11.2026 следует учитывать [квоты Free и их область действия](https://supabase.com/docs/guides/platform/billing-on-supabase), [паузу при низкой активности](https://supabase.com/docs/guides/platform/free-project-pausing) и [лимиты функций](https://supabase.com/docs/guides/functions/limits). Перед созданием проверить действующие условия и квоты аккаунта. Платные услуги без согласия не подключать.

## ADR-003. Локальная разработка и первый запуск

**Решение:** стандартный путь — Supabase CLI и работающий Docker-совместимый runtime, без подключения реальных финансовых данных на разработке. Flutter-каркас создаётся на этапе 1 исключительно для проверки backend; навигация и полноценная структура экранов остаются на этапах 2 и 4.

**Причина:** локальное воспроизведение миграций и проверок безопаснее работы непосредственно с реальными данными. В ходе этапа 2 пользователь установил Docker Desktop; локальный Supabase запущен через CLI, настройки Docker ограничивают доступ к портам localhost. Для Flutter-проверок в песочнице использовалась временная копия SDK.

## ADR-004. Проверяемая изоляция данных

**Решение:** Auth, RLS на пользовательских таблицах, ограничения целостности и отдельные политики приватного Storage. Взаимосвязи сущностей также проверяют владельца; серверные функции проверяют пользователя и не доверяют переданному `user_id`. Публичный клиентский ключ не даёт обходить RLS; привилегированные ключи и секреты остаются на сервере.

**Причина:** даже персональное приложение проектируется с возможностью нескольких пользователей и содержит чувствительные данные. Изоляция требует проверок как минимум с двумя пользователями и проверки доступа к объектам Storage.

## ADR-005. Точные деньги и осторожное сопоставление

**Решение:** избегать двоичных чисел с плавающей точкой для денег; для начального баланса выбран `numeric` с проверками, см. ADR-009. Формат сумм операций и правила округления определяются перед их реализацией. Хранить исходные суммы и валюты покупки и счёта, не выдумывать курсы. Автоматически объединять операции и классифицировать переводы только при достаточных проверенных признаках; неоднозначность оставлять пользователю.

**Причина:** корректность расчётов и сохранность исходных данных важнее агрессивной автоматизации. Нужны отдельные тесты граничных значений и ошибок сопоставления.

## ADR-006. Детализация по фактической необходимости

**Решение:** feature-first во Flutter, серверные границы по предметным областям, никаких отдельных микросервисов. Riverpod/GoRouter/Drift и функциональные модули подключать на предусмотренных этапах, при фактической потребности. Отдельный исполнитель фоновых задач пока не выбран; для Web обновлённым ТЗ выбран Cloudflare Pages на этапе 4.

**Причина:** раннее усложнение и предположения о тарифах или нагрузке не помогают выполнить первый этап. При расширении проверить ограничения выбранной платформы и совместимость актуальных стабильных зависимостей.

## ADR-007. Созданный проект Supabase и проверка подключения

**Решение:** использовать созданный владельцем проект Cash Radar в `ap-northeast-1` (Токио); владелец подтвердил этот регион после обсуждения европейского размещения. Flutter-каркас этапа 1 ограничен диагностикой соединения. Миграция добавляет только функцию проверки, пользовательские и финансовые таблицы не создаются.

**Причина:** это позволяет проверить связку Flutter → Supabase Data API → PostgreSQL в рамках требований этапа 1. 11.11.2026 миграция применена, проверен вызов функции из Flutter-клиента с публичным ключом. Запросом к метаданным БД также подтверждены права ролей и режим security invoker.

## ADR-008. Email и пароль через Supabase Auth

**Решение:** регистрация с подтверждением email, вход, выход и восстановление через Supabase Auth с PKCE. Сессии на Android/iOS хранятся в защищённом хранилище платформы; Web использует хранилище Supabase SDK в браузере. Отдельный сервис изолирует UI от SDK. Для тестов развёрнут локальный Supabase с Mailpit и тестовыми пользователями.

**Причина:** выбран пользователем, поддерживает восстановление доступа и не требует стороннего OAuth-провайдера. Ограничения встроенной облачной почты и необходимость SMTP для произвольных адресов указаны в [настройке](setup.md). Реальные финансовые данные, RLS их таблиц и проверка Storage остаются на последующих этапах.

## ADR-009. Основа данных и изоляция пользователей

**Решение:** `auth.users` остаётся источником учётных записей, `profiles` связан по `id`; `banks` — общий справочник только для чтения, `accounts` и `categories` принадлежат пользователю. RLS и ограниченные права PostgreSQL действуют совместно. Клиент не задаёт и не меняет `user_id` напрямую; он устанавливается значением `auth.uid()`. Новому и уже существующему пользователю добавляются профиль и собственные начальные категории.

Родитель категории проверяется составным внешним ключом по владельцу; защита и блокировки предотвращают циклы. Начальный баланс — `numeric` с проверкой диапазона и не более четырёх дробных знаков без округления. На этапе 5 клиентский обмен суммами должен сохранять точность: JSON-число, декодированное в Dart `double`, не гарантирует точность PostgreSQL `numeric`. Текущий баланс и основная валюта пользователя будут определены на этапах 5–6, после появления операций и настройки валюты. Архивация счёта предусмотрена через `is_active`; удаление счёта клиенту не разрешено.

**Причина:** копии категорий можно менять независимо, а ограничения базы защищают данные даже при прямом обращении к API. Тесты проверяют двух пользователей, права, создание профиля, точность суммы, связи и одновременное изменение иерархии. Финансовых операций и тестов их RLS на этом этапе ещё нет.

Миграции `20261111010000_foundation.sql` и `20261111010100_category_hierarchy_lock.sql` применены к облачному Cash Radar 11.11.2026. Проверены RLS всех четырёх таблиц, запрет анонимного доступа, три банка и начальные данные ранее зарегистрированного пользователя.
