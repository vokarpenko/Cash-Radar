# Сбор выписок из Gmail

Сборщик рассчитан на **отдельный** Gmail, предназначенный только для банковских выписок. Доступ к личной почте не подключайте. Каждая метка входящих писем явно привязана к одному счёту CashRadar. Письма остаются в Gmail; при успешной подготовке к ним добавляется метка обработанных и удаляется только исходная пользовательская метка. Входящие, прочитанное состояние и письма не удаляются.

В первой версии поддерживаются XLSX Ameria и Альфа-Банка. ACBA с паролем отложен: пароль не хранится, защищённые вложения автоматически не обрабатываются. Как и при ручной загрузке, результат попадает в предпросмотр, где пользователь решает вопросы дублей и подтверждает операции. По метке нельзя надёжно подтвердить подлинность отправителя: проверяйте выписку и счёт перед подтверждением. Приложение не отправляет содержимое писем в Gemini.

## Ограничения Google

Сборщик запрашивает `gmail.modify`: разрешение позволяет читать всю почту ящика, создавать и отправлять письма, изменять метки и перемещать письма в корзину. CashRadar использует чтение и изменение меток. Оно предоставляется всему выделенному ящику, не отдельной метке. У [Google это restricted scope](https://developers.google.com/workspace/gmail/api/auth/scopes). Для личного использования возможны [исключения из проверки приложения](https://support.google.com/cloud/answer/13464323), но действуют политика Google и предупреждение о непроверенном приложении. При External + Testing [refresh token истекает через 7 дней](https://developers.google.com/identity/protocols/oauth2#expiration); после этого потребуется повторная авторизация. Для публичного сервиса требования Google нужно рассматривать отдельно.

## 1. Подготовка Google

1. Создайте или выберите проект в Google Cloud Console и включите Gmail API.
2. Google Auth Platform → Branding: создайте приложение. Выберите External и статус Testing.
3. Audience → Test users: добавьте отдельный Gmail. В Data Access добавьте `https://www.googleapis.com/auth/gmail.modify`.
4. Clients → Create Client → Desktop app. Сохраните Client ID и Client secret. Не присылайте их в чат и не добавляйте в Git.
5. В выделенном Gmail создайте пользовательские метки, например `CashRadar/Alfa`, `CashRadar/Ameria` и `CashRadar/Done`. Создайте фильтры, присваивающие каждую входящую метку только выпискам конкретного счёта. Если у одного банка несколько счетов, им нужны разные метки и достаточно точные фильтры. Настройте пересылку банковских писем с личной почты на выделенную; сначала проверьте правила на безопасных тестовых письмах.
6. Из корня репозитория запустите `python3 scripts/gmail_oauth.py`. Введите адрес **отдельного** Gmail, Client ID и скрытым вводом Client secret. В открывшемся браузере авторизуйте именно этот аккаунт. Скрипт проверит адрес и сохранит токен в `supabase/functions/.env.gmail` с правами только владельца. Он также покажет имена и идентификаторы пользовательских меток. Файл исключён из Git; не отправляйте его содержимое в чат.

Скрипт не перезаписывает существующий файл. Для переподключения временно переименуйте старый `.env.gmail` в защищённом месте, выполните авторизацию и затем удалите старый файл; обновите секреты в нужном окружении. Не храните резервные копии токенов в репозитории.

## 2. Маршруты и локальный запуск

Найдите UUID пользователя и его активных счетов в **локальном** Supabase Studio: Authentication → Users и Table Editor → accounts. В `supabase/functions/.env.gmail` добавьте строки (подставьте собственные UUID и ID пользовательских меток из вывода скрипта):

```dotenv
GMAIL_OWNER_USER_ID=00000000-0000-4000-8000-000000000000
GMAIL_DONE_LABEL_ID=Label_123
GMAIL_ROUTES_JSON=[{"labelId":"Label_456","accountId":"00000000-0000-4000-8000-000000000001","bankCode":"alfa_ru"},{"labelId":"Label_789","accountId":"00000000-0000-4000-8000-000000000002","bankCode":"ameria_am"}]
```

Настройте только нужные маршруты. Метка одного маршрута должна быть уникальной и не совпадать с меткой обработанных. Сборщик проверяет активность и банк выбранного счёта, но не угадывает номер счёта из файла: неправильный Gmail-фильтр может направить выписку на неверный счёт того же банка и валюты. Поэтому сверяйте счёт в предпросмотре.

Запустите локальный Supabase и Edge Functions с файлом настроек:

```sh
npx --yes supabase@3 functions serve gmail-collector --network-id cash-radar-loopback --env-file supabase/functions/.env.gmail
```

Чтобы выполнить **одну локальную проверку**, потребуется локальный service role key из `supabase status`. Не копируйте ключ в чат и не используйте облачный ключ для localhost. Вместо помещения ключа в историю команд используйте скрытый ввод в терминале:

```sh
read -s 'CASHRADAR_LOCAL_SERVICE_KEY?Local service role key: '
printf '\n'
curl --silent --show-error -X POST http://127.0.0.1:54321/functions/v1/gmail-collector \
  -H "Authorization: Bearer $CASHRADAR_LOCAL_SERVICE_KEY" \
  -H "apikey: $CASHRADAR_LOCAL_SERVICE_KEY"
unset CASHRADAR_LOCAL_SERVICE_KEY
```

Проверьте раздел «Импорт → Выписки из Gmail» и подготовленные выписки. Используйте тестовые письма и локальный счёт; локальная база не содержит production-счета и операций.

## 3. Облачная настройка и расписание

Не включайте расписание до проверки локального сценария и назначения маршрутов production-счетам. Коммит и слияние публикуют функцию, но сами по себе не включают сбор почты.

1. Подготовьте отдельный файл секретов для production: те же OAuth-поля, выделенный Gmail, production UUID пользователя и счетов и нужные ID меток. Этот файл должен быть вне Git. Загружайте его через `supabase secrets set --env-file <путь>` в **проверенный** проект. Следите за тем, чтобы случайно не перезаписать существующие секреты.
2. В Supabase Vault целевого проекта создайте по одному секрету `gmail_project_url` (HTTPS URL проекта без завершающего слеша) и `gmail_service_role` (именно legacy JWT service_role key целевого проекта, соответствующий `SUPABASE_SERVICE_ROLE_KEY` функции). Это отдельные секреты Vault для Cron; клиентский publishable key и ключи формата `sb_secret_...` не подходят этому защищённому JWT-вызову. Не показывайте серверный ключ в чате, Git или истории команд. См. [рекомендацию Supabase по Vault и Cron](https://supabase.com/docs/guides/functions/schedule-functions).
3. Проверьте целевой проект и содержимое `scripts/enable_gmail_cron.sql`, затем выполните его в SQL Editor этого проекта. Он включает вызов каждые 15 минут. Для остановки: `select cron.unschedule('cash-radar-gmail-collector');`.
4. Проверьте состояние в разделе импорта и журнал Edge Function. В логах только коды ошибок и счётчики, без содержимого сообщений и токенов.

При ошибке OAuth переподключите аккаунт и обновите `GMAIL_REFRESH_TOKEN` в секретах соответствующего окружения. При отключении интеграции остановите Cron, отзовите доступ приложения в Google Account → Security → Third-party access и удалите Gmail-секреты из Supabase; письма не удаляются.
