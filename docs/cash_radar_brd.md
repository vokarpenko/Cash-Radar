# 2. Описание продукта

Приложение предназначено для личного финансового учёта.

Необходимо автоматически собирать банковские операции из нескольких банков, распознавать категории расходов и доходов, учитывать переводы между собственными счетами, строить аналитику и предоставлять удобный интерфейс для управления личными финансами.

### Подключаемые банки

На первом этапе приложение должно учитывать три банка:

- Альфа-Банк (Россия).
- ACBA Bank (Армения).
- Ameria Bank (Армения).

В дальнейшем архитектура должна позволять добавлять новые банки без существенного изменения существующей системы.

### Основная идея

Пользователь не должен вручную вносить каждую покупку.

Источники операций:

1. Банковские выписки, получаемые по электронной почте.
2. Уведомления Android от Google Wallet и банковских приложений.
3. Ручная загрузка банковских выписок.
4. В будущем — официальные API банков, если они будут доступны.

Источники могут сообщать об одной и той же операции. Поэтому система должна уметь объединять дубликаты и определять наиболее достоверную версию операции.

Банковская выписка считается основным источником подтверждённых операций. Push-уведомления являются предварительным источником информации.

# 5. Основные сущности и модель данных

### Transaction

Финансовая операция.

Необходимо предусмотреть следующие поля:

- id;

- source;
- external_id;

- suggested_category_id;
- categorization_source;
- confidence;
- import_batch_id;
- created_at;
- updated_at.

Учитывай, что одна операция может содержать сумму покупки в исходной валюте и сумму фактического списания в валюте банковского счёта.

Например, покупка в AMD с карты, привязанной к RUB-счёту, должна хранить обе суммы и обе валюты.

Не теряй исходное описание и исходные данные банка при нормализации.

Статусы операции:

- pending;
- confirmed;
- unmatched;
- cancelled.

Источники операции:

- email;
- android_notification;
- statement;
- manual;

Категории доходов и расходов.

Категории должны иметь возможность группировки по родительским категориям.

Необходимо хранить:

- источник;

- период выписки;

Правила автоматической категоризации.

Соответствие разных названий одного торгового предприятия нормализованному названию.

# 6. Бизнес-логика

### 6.1. Мультивалютность

Приложение должно поддерживать несколько валют.

Минимально необходимые:

- AMD;
- RUB;
- USD;
- EUR.

У пользователя должна быть основная валюта для отображения аналитики.

Предусмотри возможность изменения основной валюты в настройках.

Не пересчитывай и не перезаписывай исходные суммы операций.

Курсы валют и конвертация должны быть отдельной логикой. Если курс не известен, не подставляй выдуманное значение.

### 6.2. Внутренние переводы

Переводы между собственными счетами не должны учитываться как расходы или доходы.

Например:

- перевод с Альфа-Банка на Ameria;
- перевод с Ameria на ACBA;
- перевод между банковским счётом и собственными наличными.

Нужно сопоставлять исходящую и входящую операции по:

- сумме;
- валюте;
- дате;
- счетам;
- комиссии;
- описанию.

Если перевод осуществлён между разными валютами, сопоставление должно учитывать возможную конвертацию.

Не объединяй операции автоматически при недостаточной уверенности.

Пользователь должен иметь возможность вручную подтвердить или отклонить предложенную связь.

### 6.3. Наличные

Снятие наличных не обязательно должно считаться расходом.

При необходимости операция снятия должна учитываться как перевод с банковского счёта на собственный наличный кошелёк.

Расход фиксируется тогда, когда пользователь фактически потратил наличные.

### 6.4. Дедупликация

Одна и та же операция может прийти из нескольких источников.

Примеры:

- сначала push-уведомление;
- затем банковское письмо;
- затем банковская выписка.

Нельзя создавать три независимые операции.

Используй несколько признаков для поиска дубликатов:

- банк;
- счёт;
- сумма;
- валюта;
- дата;
- merchant;
- внешний идентификатор;
- исходное описание.

Приоритет источников и обновление данных должны быть предсказуемыми.

Если push-операция была предварительной, а затем появилась подтверждённая запись из выписки, обновляй существующую операцию либо связывай записи, а не создавай лишнюю.

### 6.5. Pending-операции

Операции из уведомлений и неподтверждённых банковских данных должны храниться отдельно от подтверждённых.

Они не должны попадать в окончательную статистику до подтверждения.

# 7. Импорт банковских выписок

Для каждого банка должен существовать отдельный парсер.

Парсинг должен быть детерминированным. Не используй AI для извлечения структурированных данных из файлов, если это можно сделать обычным парсером.

### Альфа-Банк

На текущем этапе доступна PDF-выписка.

Необходимо извлекать:

- дату операции;
- дату проводки;
- код операции;
- описание;
- сумму;
- валюту;
- MCC;
- сумму списания в валюте счёта, если она отличается от валюты покупки.

Для карточных операций важно сохранять исходную валюту покупки и фактическую сумму списания.

### Ameria Bank

Доступны форматы XLSX, XML и PDF.

Начинать с XLSX.

Извлекать:

- дату;
- сумму;
- валюту;
- тип операции;
- описание;
- merchant;
- остаток;
- информацию о входящих и исходящих операциях.

Не считай итоговые суммы и остатки самостоятельными транзакциями.

### ACBA Bank

Начинать с XLSX.

Заголовки могут быть на армянском языке.

Необходимо извлекать:

- дату операции;
- дату проводки;
- сумму;
- валюту;
- тип операции;
- остаток;
- описание;
- торговую точку;
- комиссию.

Строки с дневными остатками не должны импортироваться как операции.

Блок неподтверждённых операций должен обрабатываться отдельно от подтверждённых операций.

### Общие требования к парсерам

Каждый парсер должен:

1. Проверять, что файл соответствует ожидаемому формату.
2. Извлекать операции.
3. Нормализовать поля.
4. Сохранять исходные данные.
5. Проверять обязательные поля.
6. Возвращать ошибки с понятным описанием.
7. Не создавать операции повторно при повторном импорте.

Предусмотри возможность добавления новых форматов без переписывания общего механизма импорта.

# 8. Получение банковских писем

Для автоматического импорта использовать отдельный Gmail-аккаунт приложения.

Не запрашивать доступ к личной Gmail-почте пользователя.

Предполагаемый сценарий:

1. Пользователь создаёт отдельный Gmail.
2. В личной почте настраивает пересылку писем от банков на выделенный адрес.
3. Backend получает доступ только к выделенному Gmail-аккаунту.
4. Backend периодически проверяет новые письма.
5. Загружает вложения.
6. Определяет банк и формат документа.
7. Запускает соответствующий парсер.
8. Сохраняет результаты.
9. Помечает обработанные письма специальной меткой.

Для MVP можно использовать периодическую проверку почты, если она доступна на выбранной инфраструктуре.

Не удаляй письма после обработки.

Обязательно обрабатывай повторные письма и одинаковые вложения без создания дубликатов.

Интеграцию Gmail реализовывать только после готовности механизма импорта и парсеров.

# 10. Категоризация через Gemini

Категоризация должна выполняться в следующем порядке:

1. Пользовательские правила.
2. MerchantAlias.
3. MCC.
4. Ранее подтверждённые соответствия.
5. Gemini API.
6. Ручная категоризация.

AI получает только неизвестные или неоднозначные операции.

Перед отправкой данных необходимо удалить:

- ФИО;
- номера карт;
- номера счетов;
- телефоны;
- адреса;
- банковские идентификаторы;
- прочие персональные данные.

Не отправляй целые банковские документы.

Для каждого запроса передавай минимально необходимые поля.

Ответ Gemini должен иметь строгую JSON-структуру:

- transaction_id;
- category_id;
- merchant_normalized;
- confidence;
- reason.

Валидируй:

- соответствие transaction_id отправленным операциям;
- существование category_id;
- допустимые значения;
- корректность типов;
- отсутствие лишних операций.

Предусмотри три уровня обработки:

- высокая уверенность — автоматическое назначение категории;
- средняя уверенность — предложение пользователю;
- низкая уверенность — ручная категоризация.

Начальные пороги можно использовать как настраиваемые значения, но не считать confidence модели достоверной вероятностью без проверки на реальных данных.

Храни информацию о том, кто и как назначил категорию:

- rule;
- mcc;
- ai;
- manual.
