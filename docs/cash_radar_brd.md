# 2. Описание продукта

Приложение предназначено для личного финансового учёта.

Необходимо автоматически собирать банковские операции из нескольких банков, распознавать категории расходов и доходов, учитывать переводы между собственными счетами, строить аналитику и предоставлять удобный интерфейс для управления личными финансами.

### Подключаемые банки

На первом этапе приложение должно учитывать три банка:

- Альфа-Банк (Россия).
- ACBA Bank (Армения).
- Ameria Bank (Армения).

В дальнейшем архитектура должна позволять добавлять новые банки без существенного изменения существующей системы.

### Основная идея

Пользователь не должен вручную вносить каждую покупку.

Источники операций:

1. Банковские выписки, получаемые по электронной почте.
2. Уведомления Android от Google Wallet и банковских приложений.
3. Ручная загрузка банковских выписок.
4. В будущем — официальные API банков, если они будут доступны.

Источники могут сообщать об одной и той же операции. Поэтому система должна уметь объединять дубликаты и определять наиболее достоверную версию операции.

Банковская выписка считается основным источником подтверждённых операций. Push-уведомления являются предварительным источником информации.

## 3.2. Backend и инфраструктура

**Основная backend-платформа — Supabase.**

Используй:

- Supabase Auth — регистрация и авторизация пользователей.
- Supabase PostgreSQL — основная реляционная база данных.

- Supabase Edge Functions — серверная бизнес-логика и интеграции.

- Row Level Security (RLS) — изоляция данных пользователей.
- Supabase CLI и Supabase Emulator/локальный стек — локальная разработка и тестирование, где это поддерживается.

Все финансовые данные должны храниться только в PostgreSQL.

Не используй Firebase Authentication, Firestore, Firebase Storage или Firebase Cloud Functions.

Не дублируй финансовые данные в других базах данных.

Архитектура должна допускать последующий перенос backend-логики и базы данных на другую инфраструктуру без переписывания всей Flutter-кодовой базы.

Не предполагай, что Edge Functions подходят для любой тяжёлой задачи.

Особенно внимательно оценивай:

Если для конкретной задачи возможностей Edge Functions недостаточно, сначала предложи варианты решения:

1. Перенести часть обработки на клиент Flutter, если это безопасно и оправданно.
2. Разбить задачу на небольшие серверные операции.
3. Использовать другой бесплатный или условно бесплатный сервис.
4. Вынести обработку в отдельный backend-процесс.

Не создавай дополнительный платный сервер без моего согласия.

Не пытайся искусственно обходить ограничения бесплатного тарифа.

# 6. Бизнес-логика

## 6.1. Мультивалютность

Приложение должно поддерживать несколько валют.

Минимально необходимые:

- AMD;
- RUB;
- USD;
- EUR.

У пользователя должна быть основная валюта для отображения аналитики.

Предусмотри возможность изменения основной валюты в настройках.

Не пересчитывай и не перезаписывай исходные суммы операций.

Курсы валют и конвертация должны быть отдельной логикой. Если курс не известен, не подставляй выдуманное значение.

## 6.2. Внутренние переводы

Переводы между собственными счетами не должны учитываться как расходы или доходы.

Например:

- перевод с Альфа-Банка на Ameria;
- перевод с Ameria на ACBA;
- перевод между банковским счётом и собственными наличными.

Нужно сопоставлять исходящую и входящую операции по:

- сумме;
- валюте;
- дате;
- счетам;
- комиссии;
- описанию.

Если перевод осуществлён между разными валютами, сопоставление должно учитывать возможную конвертацию.

Не объединяй операции автоматически при недостаточной уверенности.

Пользователь должен иметь возможность вручную подтвердить или отклонить предложенную связь.

## 6.3. Наличные

Снятие наличных не обязательно должно считаться расходом.

При необходимости операция снятия должна учитываться как перевод с банковского счёта на собственный наличный кошелёк.

Расход фиксируется тогда, когда пользователь фактически потратил наличные.

## 6.4. Дедупликация

Одна и та же операция может прийти из нескольких источников.

Примеры:

- сначала push-уведомление;
- затем банковское письмо;
- затем банковская выписка.

Нельзя создавать три независимые операции.

Используй несколько признаков для поиска дубликатов:

- банк;
- счёт;
- сумма;
- валюта;
- дата;
- merchant;
- внешний идентификатор;
- исходное описание.

Приоритет источников и обновление данных должны быть предсказуемыми.

Если push-операция была предварительной, а затем появилась подтверждённая запись из выписки, обновляй существующую операцию либо связывай записи, а не создавай лишнюю.

## 6.5. Pending-операции

Операции из уведомлений и неподтверждённых банковских данных должны храниться отдельно от подтверждённых.

Они не должны попадать в окончательную статистику до подтверждения.

- merchant;
- остаток;
- информацию о входящих и исходящих операциях.

Не считай итоговые суммы и остатки самостоятельными транзакциями.

## ACBA Bank

Начинать с XLSX.

Заголовки могут быть на армянском языке.

Необходимо извлекать:

- дату операции;
- дату проводки;
- сумму;
- валюту;
- тип операции;
- остаток;
- описание;
- торговую точку;
- комиссию.

Строки с дневными остатками не должны импортироваться как операции.

Блок неподтверждённых операций должен обрабатываться отдельно от подтверждённых операций.

## Общие требования к парсерам

Каждый парсер должен:

1. Проверять, что файл соответствует ожидаемому формату.
2. Извлекать операции.
3. Нормализовать поля.
4. Сохранять исходные данные.
5. Проверять обязательные поля.
6. Возвращать ошибки с понятным описанием.
7. Не создавать операции повторно при повторном импорте.

Предусмотри возможность добавления новых форматов без переписывания общего механизма импорта.

Не загружай большие файлы в Edge Functions без предварительной проверки ограничений.

Если парсинг выполняется на клиенте, сервер всё равно должен проверять структуру, допустимые значения, принадлежность счёта пользователю и отсутствие повторного импорта.

# 8. Получение банковских писем

Для автоматического импорта использовать отдельный Gmail-аккаунт приложения.

Не запрашивать доступ к личной Gmail-почте пользователя.

Предполагаемый сценарий:

1. Пользователь создаёт отдельный Gmail.
2. В личной почте настраивает пересылку писем от банков на выделенный адрес.
3. Backend получает доступ только к выделенному Gmail-аккаунту.
4. Backend периодически проверяет новые письма.
5. Загружает вложения.
6. Определяет банк и формат документа.
7. Запускает соответствующий парсер.
8. Сохраняет результаты.
9. Помечает обработанные письма специальной меткой.

Для MVP можно использовать Supabase Cron и Edge Function для периодической проверки почты, если это укладывается в доступные лимиты.

Не запускай бесконечные фоновые процессы внутри Edge Functions.

Если обработка письма или вложения не укладывается в ограничения выполнения, разбивай процесс на небольшие этапы с сохранением состояния.

Не удаляй письма после обработки.

Обязательно обрабатывай повторные письма и одинаковые вложения без создания дубликатов.

Интеграцию Gmail реализовывать только после готовности механизма импорта и парсеров.

Не запрашивать доступ к личной Gmail-почте пользователя ни на одном этапе.

# 10. Категоризация через Gemini

Категоризация должна выполняться в следующем порядке:

1. Пользовательские правила.
2. MerchantAlias.
3. MCC.
4. Ранее подтверждённые соответствия.
5. Gemini API.
6. Ручная категоризация.

AI получает только неизвестные или неоднозначные операции.

Перед отправкой данных необходимо удалить:

- ФИО;
- номера карт;
- номера счетов;
- телефоны;
- адреса;
- банковские идентификаторы;
- прочие персональные данные.

Не отправляй целые банковские документы.

Для каждого запроса передавай минимально необходимые поля.

Ответ Gemini должен иметь строгую JSON-структуру:

- transaction_id;
- category_id;
- merchant_normalized;
- confidence;
- reason.

Валидируй:

- соответствие transaction_id отправленным операциям;
- существование category_id;
- допустимые значения;
- корректность типов;
- отсутствие лишних операций.

Предусмотри три уровня обработки:

- высокая уверенность — автоматическое назначение категории;
- средняя уверенность — предложение пользователю;
- низкая уверенность — ручная категоризация.

Начальные пороги можно использовать как настраиваемые значения, но не считать confidence модели достоверной вероятностью без проверки на реальных данных.

Храни информацию о том, кто и как назначил категорию:

- rule;
- mcc;
- ai;
- manual.

Также сохраняй модель и версию промпта.

Если пользователь исправляет категорию, система должна иметь возможность запомнить это соответствие и применять его к похожим операциям.

### Накопление правил по результатам AI

При интеграции AI необходимо уменьшать число повторных обращений и постепенно накапливать пользовательские соответствия:

- До вызова AI применять пользовательские правила, алиасы, MCC и ранее сохранённые соответствия. Уже распознанные операции повторно в AI не отправлять.
- Группировать неизвестные операции одного пользователя по надёжно определённому нормализованному merchant и типу операции; в пределах пакета запрашивать классификацию один раз на группу. Не считать одинаковые операции, повторные загрузки и повторные вызовы независимыми подтверждениями.
- После валидации ответа автоматически создавать узкое соответствие для этого пользователя и конкретного нормализованного merchant и типа операции, когда результат удовлетворяет настраиваемым требованиям к уверенности и качеству идентификации и не противоречит существующим решениям. Подтверждённое пользователем соответствие также можно сохранить. Не создавать по ответу AI широкие правила по подстроке или всему MCC.
- Неоднозначные и противоречивые случаи оставлять предложением для пользователя или на ручную обработку; при необходимости накапливать несколько независимых подтверждений. Уверенность модели не считать доказанной вероятностью без проверки.
- Хранить происхождение соответствия, категорию, нормализованный merchant, тип операции, модель и версию промпта. Показывать автоматически созданные соответствия в настройках; пользователь может их исправить, отключить или удалить. Его явное правило и исправление имеют приоритет над выводом AI; при исправлении прежнее автоматическое соответствие не должно продолжать переопределять выбор.
- Создание и применение соответствий выполнять идемпотентно, с изоляцией пользователей и без автоматического изменения прошлых операций. Повторное появление merchant должно использовать сохранённое соответствие без вызова AI.

Отправлять AI только минимальные обезличенные данные, необходимые для категоризации; не передавать суммы, полные выписки, персональные сведения и банковские идентификаторы, если они не нужны для этой задачи. При недоступности AI сохраняется ручная и детерминированная категоризация.

# 12. Безопасность

Финансовые данные являются чувствительными.

Обязательные требования:

- Row Level Security для пользовательских таблиц.
- Проверка авторизации на сервере.
- Никаких секретных ключей в клиентском приложении.
- Не хранить пароли банков.
- Не реализовывать автоматическую авторизацию в интернет-банках.

Не полагайся исключительно на фильтрацию данных во Flutter. Изоляция пользователей должна обеспечиваться на стороне PostgreSQL и Supabase.

10. Добавляй тесты для финансовых расчётов, импорта, дедупликации и категоризации.
11. Не используй mock-данные в production.
12. Не скрывай ошибки через пустые catch.
13. Не добавляй фиктивную реализацию функциональности.
14. Не заявляй, что функциональность работает, пока она не проверена.
15. Не выполняй необратимые действия в облачной инфраструктуре без моего согласия.
16. Не создавай платные ресурсы без моего согласия.

20. Проверяй актуальные лимиты бесплатных сервисов перед использованием возможностей, которые могут привести к оплате.
